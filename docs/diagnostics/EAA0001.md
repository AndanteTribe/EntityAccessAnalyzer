# EAA0001: Do not expose public write access

English | [日本語](EAA0001.ja.md)

| Property | Value |
| --- | --- |
| Category | EntityAccessAnalyzer |
| Default severity | Error |
| Enabled by default | Yes |
| Code fix | None |

## Message

> Entity '{0}' exposes public write access through member '{1}'

`{0}` is the entity and `{1}` is the member exposing write access.

## Cause

An entity exposes one of the following:

- A public property or indexer `set` accessor.
- A public field that can be reassigned.
- A writable `ref` return.
- A public ref field whose reference can be reassigned or whose referent can be written to.

This rule restricts APIs that let consumers in other assemblies directly change entity state.
It applies to public entity types in namespaces selected by `EntityAccessScopeAttribute`.
For the types analyzed, see [Analysis Scope](../../README.md#analysis-scope).

## Violation

The examples assume `[assembly: EntityAccessScope("App.Entities", "App.Entities.*")]`
is configured in another file. Each example is independent.

```csharp
namespace App.Entities;

public class Player
{
    private int _score;

    public string Name { get; set; } = ""; // EAA0001: public setter
    public int Level;                     // EAA0001: writable field
    public ref int Score => ref _score;   // EAA0001: writable reference
}
```

## Fix

Restrict write access while keeping read access public.

```csharp
namespace App.Entities;

public class Player
{
    private int _score;

    public string Name { get; internal set; } = "";
    public readonly int Level;
    public ref readonly int Score => ref _score;

    public Player(int level, int score)
    {
        Level = level;
        _score = score;
    }
}
```

Use `internal` to allow changes within the assembly, or `private` to limit changes to the entity itself.
A public `init` accessor is also allowed when consumers should supply a value during initialization.

## Allowed APIs and limitations

- Public constructors and public `init` accessors are allowed.
- Public `const` / `readonly` fields and `ref readonly` returns are allowed.
- Subscription to and removal from public events are allowed.
- Explicit interface implementations are allowed.
- A `readonly ref` field is prohibited because its referent is writable.
- A `ref readonly` field is prohibited because the reference itself can be reassigned.
- A `readonly ref readonly` field is allowed because it restricts both operations.

Public getters are allowed; their exposed types are checked by [EAA0003](EAA0003.md) / [EAA0004](EAA0004.md).
Indexers follow the same rules as properties.
Custom event `add` / `remove` accessor bodies are not inspected.

`readonly` does not make a referenced object immutable. For example,
`public readonly List<int> Values` is subject to [EAA0003](EAA0003.md), rather than this rule.

A derived type cannot simply narrow the accessibility of an inherited public setter.
In that case, review the base type's public API or the inheritance relationship.

## Inheritance and Diagnostic Locations

The following reporting rules apply to EAA0001–EAA0004.

Base members hidden under C# member lookup rules are excluded; the presence of the `new` keyword alone does not determine hiding. Access to hidden members through a cast to the base type is permitted. For method overloads and interface implementations, see [EAA0002](EAA0002.md#inheritance-and-interface-implementations).

Directly declared violations are reported on the relevant member or accessor. Violations in inherited or generated APIs are reported on the entity's type declaration or base-type reference, identifying the originating declaration. Its source location is included as an additional location when available. The diagnostic ID depends on the violation, not whether the API is inherited or generated.

Messages include the entity and member names; type-related diagnostics also include the offending type. Independent violations are reported together. For example, `public List<int> Values;` triggers both EAA0001 and EAA0003; adding `readonly` does not resolve EAA0003. Different analysis paths do not produce duplicate reports of the same violation on the same member.

## Configuration

```editorconfig
[*.cs]
dotnet_diagnostic.EAA0001.severity = error
```

Use `warning` to report a warning or `none` to disable this rule. For a local suppression,
use `#pragma warning disable EAA0001` and `#pragma warning restore EAA0001`.
